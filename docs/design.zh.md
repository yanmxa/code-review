# code-review 设计文档

这份文档讲的是**为什么这样设计**，以及每个决定放弃了什么。实现细节看代码和注释，这里只写取舍。

---

## 1. 整体结构

```
PR URL
  │
  ├─ parseTarget ──────────── 解析 GitHub/GitLab 链接
  ├─ adapter.fetchPr ──────── REST 拉 PR 元信息 + 完整 unified diff（不 clone）
  ├─ redactor.redact ──────── 脱敏（此后所有字符串都是 Redacted<string>）
  ├─ RunStore.open ────────── 按 (PR, head SHA) 找到或新建断点
  ├─ planUnits ────────────── 切分成评审单元（默认一个文件一个）
  │
  └─ 逐单元（顺序）:
       ├─ runRules ────────── 确定性规则（零成本，产出 adoptable 证据）
       ├─ reviewUnit ──────── pi-agent-core 的 Agent 循环
       │    └─ streamFn ───── 预算闸门 + 模型降级 + trace 写入（唯一拦截点）
       ├─ gradeAgentFinding ─ 按证据定级
       └─ store.completeUnit  findings 先落盘 → 再写 state
  │
  ├─ dedupe ───────────────── 按 fingerprint 合并
  └─ 报告 / TUI 分诊 / 回评
```

主流程（`src/engine/pipeline.ts`）只知道**顺序**，不知道**内容**：有哪些工具、哪些规则、怎么定级、什么时候降级，全都在别处。这是"新增工具不改主流程"能成立的前提，不是一句口号。

## 2. 三个关键取舍

### 2.1 一个文件一个 agent 循环，而不是整个 PR 一次调用

**选择**：每个评审单元起一个独立的 `Agent`，带只读工具，以 `submit_findings` 收尾。

**为什么不整个 PR 一次调**：
- 上下文会随 PR 大小线性膨胀，大 PR 直接爆窗口；
- 断点没有意义 —— 崩了就是全丢；
- 预算失去了控制点，一次调用要么成功要么白花；
- 模型注意力被稀释，实测对后面的文件质量明显下降。

**为什么不整个 PR 一个 agent 循环、让它自己遍历文件**：
- 那样"评审到哪了"变成模型的内部状态，无法可靠地做断点；
- 一个文件的失败会污染整个会话的上下文。

**代价**：跨文件的问题（改了一处没改另一处）单个循环看不见。补偿手段是 `search_diff` 工具 —— agent 可以主动搜索整个 PR 的改动行来验证怀疑。实测中它确实会用（trace 里能看到它搜 `\.query\(` 来确认调用点）。这比"再加一轮全局 pass"便宜得多，也更聚焦。

**顺序而非并行**：并行能快 3-4 倍，但会让花费顺序不确定，降级链的触发点随机，断点语义复杂化，TUI 也不再是一条可读的叙事。对一个几分钟就跑完的任务，这个速度不值得换掉这些性质。`--concurrency` 留作以后。

### 2.2 预算和追踪挂在 stream function 上

pi-agent-core 的 `Agent` 接受一个注入的 `streamFn`。我们包了一层：

```
authorize() → 决定能不能调、用哪个模型
  → 写 llm_request（完整 prompt）
    → 真正调用 provider
      → 写 llm_response（原始回复 + 用量）→ 记账
```

**为什么放这里而不是放在 pipeline 的循环里**：agent 循环里的 LLM 调用次数不是流程决定的 —— 模型可能连续调好几轮工具。如果预算检查放在"每个单元之前"，一个单元内部就可以无限花钱。放在 stream function 上，**下一次调用**就能生效，降级可以发生在单元中间。

同样的道理让"每条评论关联一条 trace"变成结构性保证而不是纪律要求：没有任何路径能绕过它去调模型。

**代价**：`streamFn` 的契约要求"不能抛异常，失败必须编码成终结事件"。所以预算耗尽也得伪装成一个正常的错误流（`budgetExhaustedStream`）。这段代码不直观，注释里写清楚了原因。

### 2.3 "可直接采纳"只认机器可复现的证据

这是整个项目里我改过一次的决定，值得完整记下来。

**最初的实现**：finding 附近（±3 行）有确定性规则命中，就把它提升为"可直接采纳"。看起来合理 —— 规则和模型都盯上了同一行，互相印证。

**测试打脸**：集成测试里，模型对 `src/cache.ts:13` 提了一条"建议给驱逐策略加注释"，同一行恰好有个 `console.log` 触发了 `console-log` 规则。于是一条纯风格建议被标成了"可直接采纳"。

**问题在哪**：位置相近不等于**说的是同一件事**。`console.log` 规则命中说明这行有个日志语句，它对"驱逐策略要不要加注释"这个论断没有任何证明力。靠位置提升，等于让这个分级失去意义。

**改后的规则**：

| 证据类型 | 来源 | 能否提升为"可直接采纳" |
| --- | --- | --- |
| `rule` | 确定性正则规则命中 | ✅ 是（规则本身就是这条 finding） |
| `static` | 静态检查工具的诊断（如 `ts_syntax_check`） | ✅ 是（任何人可复现） |
| `llm` | 模型推理 | ❌ 否 |

规则命中**自己产出自己的 finding**，本来就是可采纳级。模型的 finding 只有在引用了静态工具的诊断、且诊断落在同一位置时才能升级。而且 prompt 里明确告诉模型"规则已经报过的不要重复"，所以模型在同一行提的本来就应该是**另一件事**。

**防伪造**：模型必须在 `supportingToolCalls` 里填工具调用 id。分级时拿这些 id 去 trace 里核对，**对不上的直接丢弃**，不是丢弃整条 finding，而是丢弃那条引用 —— 于是它自然掉回"仅供参考"。编造引用不会被奖励。有测试专门验证这一点。

**`--verify` 为什么不改变分级**：让第二个模型复核，同意就升级 —— 这很诱人，但模型之间互相同意不是确定性，两个模型可以一起错。所以 `--verify` 只在报告里标注"复核模型同意/不同意"，分级不动。

## 3. 断点设计

### 3.1 run id 由内容决定

```
runId = sha256(platform:owner/repo:number:headSha)[0..12]
```

**结果**：重跑同一条命令**就是**续跑，用户不需要记住任何 run id，也不需要加 `--resume`。PR 有了新提交（head SHA 变了）就是一次新的运行，不会拿旧结果糊弄人。

### 3.2 写入顺序是整个设计的核心

```
completeUnit():
   1. findings.jsonl  ← 追加（append-only）
   2. state.json      ← 原子写入（临时文件 + rename）
```

**为什么是这个顺序**：崩在两步之间，重启后这个单元还是 `pending`，会重跑一次 —— 代价是几分钱。反过来的顺序（先写 state 后写 findings）崩在中间就会**永久丢失一个已经付过费的 finding**。宁可重算，不可丢结果。

**副作用**：`findings.jsonl` 可能包含重复条目。这是可以接受的 —— 追加写是它崩溃安全的原因。所有把 findings 展示给用户的地方都会先 `dedupe()`。（这里踩过坑：`browseRun` 一开始漏了去重，TUI 里出现重复条目，补了测试。）

### 3.3 中断的单元怎么处理

启动时把 `in_progress` 重置为 `pending`。**已花的钱留在账本上** —— token 是真的消耗掉了，假装没花过会让预算变成谎话。

### 3.4 diff 变了怎么办

`state.json` 里存 `diffHash`。对不上就说明 PR 在断点之后被改过，此时**丢弃断点重新开始**，并明确告诉用户，而不是把新旧结果混在一起。

## 4. 预算

| 阈值 | 动作 |
| --- | --- |
| 50% | 降级到 mini |
| 75% | 收缩上下文（`get_file` 上限 2000 行 → 400 行，跨文件 pass 关闭） |
| 85% | 降级到 nano |
| 100% | 硬停 |

**降级链单向**：只降不升。可逆的降级会让成本曲线不单调，用户也会困惑。

**硬停之后仍然跑确定性规则**。这是个刻意的决定：规则零成本，而且产出的恰恰是最高价值的发现（密钥泄漏、SQL 注入）。因为 LLM 没钱了就把免费检查也一起跳过，是把"部分结果"变成"截断结果"。实测 `--budget 0.12` 时，4 个文件只有 1 个过了 LLM，报告里仍有 5 条可采纳意见。

**成本从哪来**：pi-ai 的 `Usage.cost.total`。但有些 provider（以及测试用的 faux provider）只回 token 不回费用，直接信它会让账本永远是 0、预算机制静默失效。所以当 `cost.total` 为 0 而 token 不为 0 时，用模型的公开价目自己算（`calculateCost`）。这个 bug 是被离线集成测试逼出来的。

## 5. 安全

### 5.1 脱敏由编译器强制

```ts
type Redacted = string & { readonly [redactedBrand]: true };
```

`Redactor.redact()` 是唯一能产出这个类型的地方（除了显式的 `Redactor.trusted()`，只用于本程序自己写的文案）。凡是要出网或落盘的接口都只接受 `Redacted` —— **忘记脱敏是编译错误，不是运行时泄漏**。

三层防护：

1. **运行时凭据种子**：启动时把 `*_TOKEN` / `*_KEY` 环境变量的**值**登记进去。就算我们自己的 token 被误回显，也进不了 trace。
2. **模式规则**：源自 gitleaks 的规则集（PEM 私钥块、AKIA、`ghp_`、`glpat-`、JWT、`user:pass@`、通用 `key = "..."` 赋值…）。
3. **熵值扫描**：≥24 字符、混合字符类、香农熵 > 4.0 的串，兜住模式没预料到的形状。

占位符形如 `[REDACTED:aws-access-key:5d3c]`，后四位是 `sha256(secret)` 的前缀 —— **稳定但不可逆**。模型仍然能推理"这两处用的是同一个凭据"，却永远看不到凭据本身。

trace 写入时会**再脱敏一次**。上游已经脱过了，这是纵深防御，对没有密钥的文本零成本。

**踩过的坑**：熵值扫描的候选正则最初把 `/` 算进 token，于是一整段 URL 路径（`com/istanbuljs/v8-to-istanbul/blob/da1c8ef.../lib/source.js`）被当成一个高熵串遮掉了。在真实 PR 上跑才发现。现在用 `isPathLike()` 区分路径和 base64（看前导字符和斜杠数量），两种情况都有回归测试。

### 5.2 不执行仓库里的任何代码

不是"我们小心不去执行"，而是**没有执行的能力**：

- 不 clone 仓库，adapter 全是 REST；
- 工具注册表里**没有** shell / exec / write 工具；
- 全程唯一的子进程是 `gh auth token`（用户本机安装的二进制，固定参数，仓库内容碰不到它）。

`ts_syntax_check` 看似例外，其实不是：它把文件内容取到内存，交给 TypeScript 编译器的**虚拟 CompilerHost**。编译器把代码当**数据**解析，`noResolve` 不去碰 import，`noEmit` 不写文件。有一条测试专门喂给它 `throw new Error(...)` + `writeFileSync` 来确认什么都没发生。

## 6. 可扩展性：为什么是显式数组而不是文件扫描

`tools/index.ts` 是一个手写的数组。也可以做成扫描目录自动发现，但显式数组：

- 有类型检查，改名重构不会悄悄失效；
- 打包/编译后仍然工作（glob 扫描在 bundle 后会挂）；
- 启用了哪些工具一眼可见，这是安全相关的信息。

代价是加工具要多改一行。这一行换来上面三条，值得。

`ToolSpec.meta` 的每个字段都有下游消费者，没有装饰性字段：

| 字段 | 谁在用 |
| --- | --- |
| `promptSnippet` | 生成 system prompt 里的工具清单 |
| `evidenceKind` | 置信度分级 |
| `platforms` | 按 GitHub/GitLab 过滤 |
| `enabledByDefault` | 与用户配置合并 |
| `costHint` | TUI 活动面板 |

**为什么 `build(context)` 是个工厂而不是直接给一个 tool 对象**：工具需要"这次评审的 PR、这个文件、当前的上下文预算"，这些在模块加载时都不存在。工厂让工具拿到这些而不必依赖全局状态。

## 7. TUI

**为什么值得做**：这个 agent 会跑几分钟并且在花钱。等待期间用户真正想知道的只有三件事 —— 现在在做什么、花了多少、找到了什么。三个区域各回答一个，没有第四样东西配得上屏幕空间。

**布局**：`TuiAltScreen` + 自绘圆角面板（pi-tui 的 `Box` 只做 padding，不画边框；而可读性几乎全靠分区）。

**配色克制**：结构用暗灰，一个强调色（青），语义色只在真的表达语义时出现 —— 绿=完成/可采纳，黄=待定/警告，红=错误/超支，品红专用于模型徽章。**什么都上色等于什么都没说**。

**预算条的颜色跟着降级链走**：条子变黄和模型变便宜是同一件事，不是两套独立的视觉语言。

**一个事件流，两个渲染器**：`Dashboard` 和 `plain.ts` 消费同一个 `RunEvent` 流。所以 CI 里看到的和终端里看到的不可能对不上 —— 关于"发生了什么"只有一个真相，只是有两种画法。

**硬性约束**：pi-tui 要求 `render(width)` 返回的每一行**可见宽度不得超过 width**，超了会破坏差分渲染。所有布局工具都用 ANSI 感知的 `visibleWidth` 强制这一点，测试在 60/80/100/140/200 列下逐行断言。

## 8. 已知限制

诚实地列出来，比藏着好：

1. **断点粒度是文件级**。崩在一个文件中间会重跑这个文件（几分钱），不是从上一次工具调用继续。更细的粒度要持久化 agent 的中间状态，复杂度不划算。
2. **`ts_syntax_check` 看不到跨模块类型**。没有 `node_modules` 和真实 tsconfig，只能查语法和文件内自洽的类型错误。这个限制写进了工具的 description，模型知道它的输出意味着什么。
3. **GitLab 回评是逐条 discussion**。GitLab 没有批量 review 接口，所以部分失败时会留下一半评论。GitHub 是一次提交，要么全成功要么整体回退到摘要评论。
4. **跨文件问题靠 `search_diff` 而非专门的 pass**。够用，但不完备。
5. **熵值扫描仍有误报可能**。占位符保留了可读性（能看出是什么类型的密钥），所以误报的代价是可控的。
6. **顺序执行**，大 PR 比并行慢 3-4 倍。

## 9. 测试策略

182 个测试，**全部离线**，不需要任何 API key：

- LLM → pi-ai 的 faux provider（可脚本化的模型回复）
- GitHub → 内存里的假 adapter
- 终端 → 自己实现的 `Terminal` 桩（pi-tui 没导出 virtual terminal）

值得说的几条：

- `test/pipeline.test.ts` 跑**完整流水线**：findings 落盘、断点写入、预算累加、trace 生成、埋入的密钥在任何产物里都搜不到。
- `test/store.test.ts` 模拟崩溃：截断 `findings.jsonl` 最后一行、留下半截的 `state.json.tmp`，验证恢复行为。
- `test/tui.test.ts` 在 5 种终端宽度下逐行断言宽度契约。
- `test/rules.test.ts` 的两条回归测试直接写明了 bug 成因（见下节）。

**几个 bug 是被测试和真实运行逼出来的**，这里如实记下：

| 问题 | 怎么发现的 |
| --- | --- |
| 就近规则命中会错误提升置信度 | 集成测试断言"模型推断=仅供参考"失败 |
| 两条安全规则永远匹配不上 | 真实 PR 上跑，SQL 注入只被模型抓到、没被规则抓到 |
| 熵值扫描把 URL 路径当密钥 | 真实 PR 上跑，看到链接被遮掉 |
| provider 不回费用时账本恒为 0 | 离线集成测试断言"花费 > 0"失败 |
| `browseRun` 读磁盘 findings 没去重 | 用真实运行数据渲染 TUI 时看到重复条目 |
| 代理配置了但 Node fetch 不用 | 第一次真实运行，4 个单元全部 "Connection error." |

最后一条尤其说明问题：如果只跑单测，这个项目会"全绿"但一条真实 PR 都评审不了。
