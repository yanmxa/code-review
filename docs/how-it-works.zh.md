# 一次评审是怎么跑完的

先讲为什么是这个形状，再讲流程。取舍论证见 [设计文档](design.zh.md)。

---

## 思路

### 评审是两件事，而它们要的东西相反

**覆盖**：每处改动都被看过。要便宜、穷尽、可断点——成本必须有上界。

**判断**：这次改动整体站不站得住。要能同时握住几个地方、自己决定往哪看——天然无界，事先不知道要读几个文件才能确认一个怀疑。

塞进同一种机制必然牺牲一件，所以分两趟：

| | 逐文件扫描 | PR 级那一趟 |
| --- | --- | --- |
| 谁决定看什么 | 程序 | 模型自己 |
| 轮次上限 | 6 | 14 |
| 输入 | 单个文件的 diff | 意图 + 全部结论 + 工具 |

**扫描要确定，思考要放开。**

### 逐文件的评审员为什么互相不通气

它换来一条硬性质：**中断后续跑的结果，和从没中断过完全一样**。

每个文件的输入只有自己的 diff、PR 描述、规则命中，不依赖"前面跑过哪些文件"。所以跳过已完成的、重做被打断的都安全。

一旦累积记忆这条就破：从第 3 个文件续跑时拿到的上下文和原本不同，同一 commit 跑两次结果不同。这个代价不值得付。

### 盲区谁来补

代价是真的：`session.ts` 的评审员看到空 `catch` 吞掉 `db.query`，但不知道同 PR 里 `retry.ts` 刚加了 `withRetry`。

PR 级那一趟为此存在，问两类问题：

- **不一致** —— 调用方没跟着被调用方改、契约单边变更、新路径绕过某个检查
- **不完整** —— 新加的东西没人用、新配置项没人读、新错误类型没人接

第二类必须单列：它对逐文件**结构性不可见**——引入那个东西的文件单独看完全完整。程序先用正则算出「这次引入了哪些名字」交给它，把需要判断力的那半留给模型：**没有调用方是疏忽，还是不关这个 PR 的事**。

### 危险和花钱的事各只有一个入口

**脱敏**在取材时完成，之后所有环节只接受 `Redacted<string>`（编译期强制）。

**预算和 trace** 挂在 pi 的 `streamFn` 上——每次 LLM 调用的必经之路。所以"下次调用就降级""每条 prompt 都在盘上"是结构上成立的，新增 PR 级那一趟不必为此写任何代码。

## 流程

```
PR URL
  │
  ├─ ① 取材   REST 拉元信息 + unified diff + CI 诊断（不 clone）
  ├─ ② 脱敏   此后每个字符串都是 Redacted<string>
  ├─ ③ 切分   一个改动文件 = 一个单元；跳过锁文件/二进制/生成物
  │           文件数 > 1 时追加 #pull-request 单元
  │
  ├─ 逐单元、顺序、互不通气 ────────────────────────────
  │    ④ 规则扫描（本地 ¥0）  只看新增行，命中 → rule 证据
  │    ⑤ Agent 循环（≤6 轮）  get_file / search_diff / get_diff
  │                           ts_syntax_check / submit_findings
  │    ⑥ 定级                 rule|static → 可采纳；仅 llm → 参考
  │    ⑦ 落盘                 findings.jsonl → state.json（原子）
  │    ⑧ 重算预测             超支就降一档模型
  │  ──────────────────────────────────────────────────
  │
  ├─ ⑨ #pull-request（≤14 轮）
  │     输入：意图 + 文件清单 + 各文件结论 + 已报过什么
  │           + 本次引入的名字（正则算出）
  │     工具：另加 list_changed_files
  │     定级按发现所指文件查 hunks，不是本单元的
  │
  └─ ⑩ 全局去重 → 报告 / TUI 分诊 / 幂等回评
```

单文件 PR 不跑 ⑨——没有"跨"可言。

## 一条发现的一生

**起点** `demo/src/config.ts` 新增一行：

```diff
+  awsAccessKeyId: "AKIAIOSFODNN7EXAMPLE",
```

**② 脱敏** 在任何东西看见它之前：

```
awsAccessKeyId: "[REDACTED:aws-access-key:1a5d]",
```

`1a5d` 是密钥 sha256 的前 4 位：同一密钥在所有地方是同一标记，且不可逆。之后模型、trace、报告拿到的都只有这个。

**④ 规则命中** `secret-in-diff` 在新增行上命中 → 产出一条 `rule` 证据的发现，**天生就是「可直接采纳」**：证据本身就是发现，任何人都能从 diff 复现。

**⑤ 模型那一趟** 规则命中作为上下文喂给模型，并告知"这些已有证据，别重复报"。

**⑥ 定级，两道闸**：

1. 锚点必须落在 diff 触及的行（±3 行吸附），落不上就丢弃——这条评论根本发不出去
2. 引用的 tool call id 拿去 trace 核对，对不上就丢掉这条引用（不是整条发现）。**编造引用不会被奖励**

| 证据 | 来源 | 可直接采纳 |
| --- | --- | --- |
| `rule` | 确定性正则命中 | ✅ |
| `static` | 静态工具诊断 | ✅ |
| `llm` | 模型推理 | ❌ |

**刻意不做**：不因"附近有规则命中"就提升档位。位置相近不等于说的是同一件事——这逻辑存在过，被测试推翻后删掉了。

### 「仅供参考」内部怎么排

模型交发现时说自己有几分把握（`◉确定` `◐多半` `○拿不准`），问法是**什么能证明你错**。它只决定组内排序（严重级优先），永远不改档位。

两个踩出来的细节：

- **字段是可选的**。设成必填时模型漏填 → schema 校验失败 → **那个文件的发现全丢**。现在漏填等同「拿不准」。
- **第一版问法是"你有把握就填 certain"，实跑回来全是 certain。** 改成可证伪的问法后才有分布。

「可直接采纳」不显示自评：在编译器诊断旁边标"拿不准"，是在怀疑一个事实。

## 再一条：只有整体视角看得见的

`retry.ts` 新增并导出 `withRetry`；`session.ts` 里 `loadSession` 直接调 `db.query`。**两个文件单独看都完整**。

程序先算出这次引入了什么（`src/engine/introduced.ts`）：

```
withRetry   ← export async function，来自 demo/src/retry.ts
```

模型自己去查：

```
→ search_diff "\bwithRetry\b"    全 PR 只有定义，没有引用
→ get_diff session.ts            那 loadSession 呢
→ submit_findings
```

产出：

> **`withRetry` 在这次改动里没有任何调用方** · 次要 · 仅供参考 · 自评 **多半**
>
> `search_diff` 只找到这里的定义，没有任何新增或修改的代码使用它。如果它是给 `loadSession` 之类的调用准备的，这次提交少了接上去的那一步；否则这个辅助函数目前是悬空的。

自评是「多半」而非「确定」——PR 之外的代码可能在用它，而它看不到。它把另一种解释写进了正文，而不是断言作者忘了。

定级查的是**发现所指文件**的 hunks；沿用逐文件那套（只认本单元的行）会把这一趟报的每一条都否掉。

## 断点续跑

**运行的身份是算出来的**：

```
runId = sha256("github:yanmxa/code-review:1:b5afa3ff…").slice(0, 12)
          ↑平台      ↑仓库              ↑PR号 ↑head SHA
```

同一 PR、同一 head commit → 必然同一目录，用户不用记任何 id。**PR 有新提交就是另一次运行**。

```
~/.code-review/runs/89acc558042e/
├── state.json      各单元状态、累计花费、降级档位、diffHash
├── findings.jsonl  追加写
├── traces/         每单元一个
└── report.md
```

| 启动时 | 动作 |
| --- | --- |
| 目录不存在 | 全新运行 |
| 目录在，diffHash 对得上 | 续跑 |
| 目录在，diffHash 对不上 | PR 被改过 → 丢弃重来并告知 |

**中断的单元重置为待办，但账不抹**——token 是真花掉了，假装没花会让预算变成谎话。

**写入顺序是核心**：

```
1. findings.jsonl   追加写
2. state.json       临时文件 + rename（原子）
```

崩在两步之间：单元仍是 `in_progress`，重启后重跑一次，代价几分钱。**反过来的顺序**会永久丢掉一条已付费的发现。宁可重算，不可丢结果。

代价是 `findings.jsonl` 会有重复——所有拿给人看的地方都先 `dedupe()`。（踩过坑：`triage` 一开始漏了去重。）

## 观测与反馈

**每条发现关联一个 trace**（`traces/<unit>.jsonl`）：完整 prompt、模型原始回复、每次工具调用与结果、逐次用量。看法：报告里的路径、TUI 里按 `t`、或 `code-review trace <run> <unit>`。

**被否掉的不再提**：发出的评论带 `<!-- code-review:f:<fingerprint> -->`。下次运行比对 PR 上还剩什么——被**删除**或线程被 **resolved** 记为否决，永久不再报；回复反驳算讨论不算判决。记忆是**仓库级**的（运行目录按 head SHA 建，放那儿会在下次 push 时蒸发，而那正是工具要重复自己的时刻）。PR 本身是持久记录，本地文件只是缓存。

一个每次 push 都重复同一条无效意见的机器人，团队学会的唯一行为是无视它。

## 各阶段成本

一次真实运行（4 个文件）：

| 阶段 | 成本 |
| --- | --- |
| ①②③ 取材/脱敏/切分 | 本地或 REST，¥0 |
| ④ 规则扫描 | 本地，**¥0** |
| ⑤ 逐文件 Agent | 大头，约 ¥0.14 |
| ⑨ PR 级那一趟 | 约 ¥0.02，**一趟，不随文件数线性增长** |
| ⑥⑦⑧⑩ | 本地，¥0 |

这解释了一个设计选择：**预算耗尽后仍然跑 ④**。规则零成本，产出的恰恰是最高价值的那几条。实测 `--budget "9k tokens"` 时 4 个文件只有 2 个过了 LLM，报告里仍有 8 条可直接采纳。

## 已知的机制缺口

- **规则只看新增行。** 删掉一个鉴权检查、拿掉一个校验，产生零条规则命中——确定性那层只覆盖"加了坏东西"，没覆盖"拿掉了好东西"。
- **`no-test-change` 是 PR 级事实却按文件报**，改 20 个文件刷 20 条；而且它是启发式不是缺陷，却在「可直接采纳」档里。
- **锚点必须落在改动行**，而最值钱的发现是"本该改而没改"——缺失的东西没有行号。上面那条 `withRetry` 锚在定义处，而非最该被看到的 `session.ts:15`。
- **去重靠标题文本**（path + 归一化标题 + 行号/5），同一问题换个说法就是两条。
- **PR 级那一趟排在最后**，降级链降到底才轮到它，预算真耗尽时整趟被跳过。
