# 关于 AI 的使用

这个项目由 AI 辅助完成。这份文档记录过程 —— 哪些是 AI 写的、怎么验证的、AI 写错了什么、错误又是怎么被发现的。

用 AI 写代码不是问题，**不知道 AI 什么时候在骗你**才是问题。所以下面重点写后者。

---

## 1. 分工

| 阶段 | 做法 |
| --- | --- |
| 框架调研 | AI 检索 pi 的文档与 npm 包。**第一轮结果是错的**（见下），靠核对真实 tarball 纠正。 |
| 架构设计 | 人定方向（独立 CLI vs pi 扩展、TUI 做到什么程度、置信度怎么定义），AI 产出方案细节。 |
| 编码 | AI 主写，人审每一处。所有判断性代码（分级规则、预算策略、脱敏规则）逐行确认。 |
| 测试 | AI 写，但**测试用例的意图由人定**：每条测试要证明什么、失败了说明什么。 |
| 验证 | 人主导。真实 PR 上跑、真的 `kill -9`、真的把预算调到不够用。 |
| 文档 | AI 起草，人改写结论部分（尤其"已知限制"和本文档）。 |

## 2. AI 出的错，以及怎么发现的

### 2.1 调研阶段：包名整个是过时的

第一轮调研给出的是 `@mariozechner/pi-*`（badlogic/pi-mono）。实际上项目在 2026 年 5 月已改名到 `@earendil-works/pi-*`（earendil-works/pi），旧包在 npm 上被标记为 deprecated。

**怎么发现的**：没有直接采信调研摘要，而是去 npm 拉了真实的 tarball，读 `dist/*.d.ts`。这也顺带纠正了几个 API 签名的细节 —— 比如 `AgentTool.execute` 并没有文档里描述的第五个 `ctx` 参数。

**教训**：AI 对"某个库怎么用"的回答，权威性来自它读过的文档，而文档可能过时。**签名以 `node_modules` 里的 `.d.ts` 为准**，这是 M0 阶段专门做的一件事。

### 2.2 模型目录里的型号和调研说的不一样

调研说 OpenAI 的降级链应该是 `gpt-5.2 → gpt-5-mini → gpt-5-nano`。实际跑 `models.getModels("openai")` 打印目录，发现有更新的 `gpt-5.4 / gpt-5.4-mini / gpt-5.4-nano` 同代三档，价格梯度更合理。

**怎么发现的**：写了 20 行脚本把目录打出来看，而不是相信摘要。

### 2.3 置信度分级：一个看起来合理、实际错误的规则

AI 实现的分级逻辑里有一条：finding 附近 ±3 行有确定性规则命中，就提升为"可直接采纳"。人审时觉得合理，通过了。

**是测试推翻了它**：集成测试断言"模型的纯推断应该是仅供参考"，却得到"可直接采纳"。查下去发现模型对 `cache.ts:13` 提的是"建议加注释"，而同一行恰好有 `console.log` 触发了规则 —— 一条风格建议被一条无关的规则背书了。

删掉这条逻辑，并在代码里写清楚为什么它不能存在。这是整个项目里最重要的一次修正：**"可直接采纳"这个标签的全部价值，就在于它不能被这样稀释**。

### 2.4 两条安全规则写出来就没法匹配

`sql-string-concat` 的正则用了 `[^;'"\`]*`，把引号排除在外。但真实的 SQL 拼接**必然**先闭合一个字符串字面量才能 `+`：

```js
db.query("SELECT * FROM sessions WHERE user_id = '" + userId + "'")
//                                                ^ 这个引号让规则永远匹配不上
```

`insecure-random` 同理：它要求 `Math.random()` 后 80 字符内出现 token/secret 之类的词，但这些词通常在**函数签名那一行**，不在调用那一行。

**怎么发现的**：单测全绿。是在真实 PR 上跑的时候，看到 SQL 注入只被模型抓到（"仅供参考"）、没被规则抓到（本该"可直接采纳"），才回头查的正则。

**教训**：正则看起来对和真的能匹配是两回事。修复后补的两条回归测试，注释里直接写明了成因。

### 2.5 provider 不返回费用时，预算机制静默失效

AI 的实现直接信任 `usage.cost.total`。但 faux provider（以及一些真实网关）只回 token 数、费用恒为 0。结果是账本永远 0、预算形同虚设 —— **一个不会报错、只会静默不生效的失败**。

**怎么发现的**：离线集成测试里断言"跑完之后花费 > 0"，红了。

改成：费用为 0 但 token 不为 0 时，用模型的公开价目自己算。这同时修好了测试和真实场景。

### 2.6 `browseRun` 读磁盘时忘了去重

`findings.jsonl` 是追加写的（这正是它崩溃安全的原因），所以续跑会让同一个单元的 findings 出现两次。pipeline 结尾有 `dedupe()`，但 `browseRun`（`code-review triage`）直接把文件内容喂给了 TUI。

**怎么发现的**：拿真实运行的数据渲染 TUI 截图时，肉眼看到重复条目。

### 2.7 代理：单测全绿，但一个 PR 都评审不了

第一次真实运行，4 个单元全部失败，trace 里是 `"Connection error."`。看起来像 API key 有问题，但 `curl` 用同一个 key 是通的。

根因：环境里设了 `HTTPS_PROXY`，`curl` 会读，**Node 的全局 `fetch` 默认不读**（需要 `NODE_USE_ENV_PROXY=1`）。

这条最能说明问题：**如果只跑单元测试，这个项目会 100% 绿，但完全不能用**。

## 3. 怎么防止"AI 写得像模像样但其实不对"

几条实际生效的做法：

**① 让编译器承担判断，而不是靠记性。** 脱敏用 branded type `Redacted<string>`，忘了脱敏是**编译错误**。这比"记得调用 redact()"可靠得多 —— 人和 AI 都会忘。

**② 测试写"要证明什么"，不写"覆盖什么"。** 每条测试对应一个可能出错的具体行为。上面 2.3 / 2.5 两个 bug 都是被这种测试逼出来的，而不是被覆盖率逼出来的。

**③ 真实运行是不可替代的。** 2.4 / 2.6 / 2.7 三个问题单测一个都发现不了。所以专门建了一个埋雷的演示仓库，在上面真的跑、真的 `kill -9`、真的把预算调到不够。

**④ 追问"这个断言凭什么成立"。** 修熵值扫描时，AI 在注释里写"带斜杠的 base64 密钥仍能被捕获"。写测试一验证 —— 不成立（分片后每段都不到 24 字符）。于是重新设计了判别规则，让注释和现实对上。**注释里的乐观断言是 AI 最常见的失真来源。**

## 4. 时间去哪了

粗略比例：

- 调研与核对 API：15%
- 编码：30%
- **测试与真实验证：40%**
- 文档：15%

写代码不是瓶颈。**确认代码真的做了它声称做的事**才是。
